# AGENTS.md

Personal repo: AI agent configurations + scripts to install them automatically.

## Supported agents

- Claude Code, Codex CLI, OpenCode, oh-my-pi (`omp` — a fork of pi with its own binary and `~/.omp` config dir), and pi itself (`~/.pi/agent`).
- When adding another: new per-agent folder + installer entry; do not break existing agents' installs.

## Layout

- One folder per agent (`opencode/`, `claude/`, `codex/`, `omp/`, `pi/`): holds that agent's Jinja2 templates (`.j2`) and other agent-specific files.
- `agents/`: shared cross-agent content — `agents/AGENTS.md` holds the common guidelines; each agent folder may add `<agent>/AGENTS.md` with agent-specific rules. `install.py` combines both into each agent's global instructions file (`~/.claude/CLAUDE.md`, `~/.codex/AGENTS.md`, `~/.config/opencode/AGENTS.md`); `~/.agents/AGENTS.md` symlinks to the common file. Keep both files lean — they load into every session's context. Agent-specific rules never go in `agents/AGENTS.md`.
- `skills/`: shared cross-agent skills, one directory per skill (`SKILL.md` + resources), linked whole into every supported agent unless the skill's frontmatter restricts it (see Install rules). Provenance + licenses of imported skills: `skills/SOURCES.md`, `third-party-licenses/`.
- `subagents/`: subagent definitions (`*.md`) and per-agent templates (`*.md.j2`), rendered with `agent` in the Jinja context so one source can carry both frontmatter dialects; linked/rendered into `~/.claude/agents` and `~/.config/opencode/agents` only (the agents that read definition files).
- `harnesses/`: task-scoped agent setups, one directory per harness (`harness.jsonc` + `AGENTS.md`, optional `skills/`). `install.py` renders them into the agent's harness location — currently pi only, `~/.pi/harnesses/<name>/`, including an executable `pi` launcher that T3 Code uses as the pi provider's binary path. Agent-format templates live in `<agent>/harness/`.
- `mcp/servers.jsonc`: canonical shared MCP server list — single source of truth, rendered into every agent config. More shared data dirs may come (e.g. models).
- `config.jsonc`: repo-wide settings (`enmaas.enabled`, `enmaas.aux_model`), schema-checked against `config.schema.json` and rendered into every agent config — flip + re-run install to switch agents between EnMaaS and their fallbacks (claude: Vertex via gcloud ADC; opencode: openai; codex: default OpenAI auth). `aux_model` names the free EnMaaS model covering claude code's cheap auxiliary usage (haiku alias + auto-mode classifier) — switch it to another free model when that one is down, or null it out for claude-haiku-5-5.
- `claude/plugins/`: our own Claude Code marketplace (`patjlm-agents-config`, directory source) — currently holds the `mcp` plugin.
- `install.py`: renders templates → agent config files. Structure: shared primitives, shared data, then one section per agent, listed in `INSTALLERS` — adding an agent = new folder + templates + one section + one list entry. Agent *formats* live in the agent's Jinja templates; agent *behavior* (symlinks, CLI calls, drift checks) in its `install.py` section. One agent failing does not abort the others.

## Install rules (important)

- Two install mechanisms:
  - **Generated configs** (e.g. `~/.config/opencode/opencode.jsonc`, `~/.claude/settings.json`): `uv run install.py` renders `.j2` templates. Generated files are never hand-edited — edit the template + shared data, re-run installer.
  - **Symlinks** for 1:1 content: `~/.agents/AGENTS.md` → repo `agents/AGENTS.md`; `~/.claude` entries link into repo `claude/`; shared skills link whole directories (see below).
- Shared skills: each `skills/<name>/` directory is symlinked as one unit into `~/.claude/skills`, `~/.agents/skills` (read by codex, pi and opencode) and `~/.omp/agent/skills` — so resources added in the repo need no reinstall, and a skill is added/removed atomically. Stale links pointing into this repo are pruned; foreign links (e.g. app-installed skills) and real dirs are left alone. Backups go under `<agent dir>/backups/` — a `.bak` directory next to the skills would be discovered as a skill. Destinations follow skillshare's maintained registry (see References) — check it before adding an agent or changing a path.
  - Default: a skill goes to every agent. `targets: [claude, omp]` in its `SKILL.md` frontmatter limits it to those agents (unknown names warn). Only skills that are very specific to one agent belong in `<agent>/skills/` (currently `claude/skills/`: `daily-status`, `subagents`) — those are linked by that agent's section only.
  - Imported third-party skills are unmodified copies; keep `skills/SOURCES.md` and the matching license files updated when adding one.
- Subagents: `subagents/*.md` are linked 1:1 file-by-file into `~/.claude/agents` and `~/.config/opencode/agents` (the only agents that read definitions). `subagents/*.md.j2` are rendered per agent with `agent` (`claude`/`opencode`), `enmaas_enabled`, `home` and `repo` in the context — that is how one definition carries Claude's frontmatter (`tools:`, `model: <alias or full id>`) and OpenCode's (`mode:`, `permissions:`, `model: provider/id`) without forking the prompt. OpenCode definitions must be v2: `permissions` is an ordered `{action, resource, effect}` list, last match wins, unmatched defaults to `ask` — read-only agents deny `edit`/`write`/`patch`/`shell`/`execute` explicitly and allow their tools (`read`/`glob`/`grep`/`webfetch`/`websearch`/`todowrite`). `targets:` in the frontmatter limits a definition; absent means both. Claude-only definitions state `targets: [claude]` (e.g. `repo-expert.md`, whose `mcpServers:`/`effort:` keys mean nothing to OpenCode). Generated definitions are not pruned when a template is removed, same as other rendered configs. Free-model routing: the web researcher runs on the free EnMaaS GLM model (`rits/zai-org/glm-5-3`, `enmaas-free/…` in OpenCode) when enmaas is enabled, and falls back to sonnet/gpt-6-luna when disabled.
- Harnesses: a harness is a task-scoped agent (own config dir, instructions, MCP servers, model, tool policy), not a coding agent — `harnesses/<name>/AGENTS.md` is standalone, not common + agent text. `harness.jsonc` names `agent`, `model` (provider/id/thinking), `mcp`, `env` (exported by the launcher before it execs the agent, after the launching app's own variables; a string sets a fixed value, `null` passes the caller's variable through with an empty default — how the Slack harness turns off T3's approval hook with `T3_PI_RUNTIME_MODE=full-access` and forwards `SLACK_MCP_READ_ONLY`), `files` (extra harness files symlinked next to `AGENTS.md`, e.g. a helper script), `extensions` (pi extensions linked and loaded with `--extension`, e.g. the Slack guard) and `excludeTools`. An `mcp` value is either a server name from `mcp/servers.jsonc` plus an override object (deep-merged over the base server, same rules as per-agent blocks) or a full definition carrying `type`/`command`/`url`, validated against `mcp/servers.schema.json` — that is how a harness-only server stays out of every regular agent. The pi config dir is `~/.pi/harnesses/<name>/`: `mcp.json` and `settings.json` rendered, `AGENTS.md` and `models.json` symlinked (`models.json` is shared with `~/.pi/agent/models.json`), `--no-skills` plus explicit `--skill` paths, and `pi` as the launcher — it sets `PI_CODING_AGENT_DIR`, the corporate CA and the tool policy, and is also the T3 Code pi provider's binary path. A harness pins its model, so it keeps working when `enmaas.enabled` flips for the coding agents; it depends on the pi install for `models.json`.
- Never duplicate config content across agent dirs — shared data lives once in repo (`mcp/`, ...), agent templates only map it to each agent's format.
- Install must be idempotent and safe to re-run: skip unchanged files, back up before overwrite, never write through symlinks, don't clobber unrelated user files.
- Claude specifics:
  - 1:1 files (`statusline-command.sh`, `commands/`, `hooks/`) are symlinked into `~/.claude`; skills and subagents come from the shared mechanisms above; `~/.claude/CLAUDE.md` is generated (common + `claude/AGENTS.md`).
  - `claude/settings.jsonc.j2` (comments + `{{ home }}`/`{{ repo }}` substitution) is rendered to plain JSON and **copied** to `~/.claude/settings.json` — never symlinked, Claude Code itself writes to it (permissions, `/config`); a symlink would let those writes hit the repo. The `unchanged` check compares parsed JSON (insensitive to Claude Code's reformatting); any differing top-level keys are warned about before overwrite (backup kept) — merge such changes into the source to keep them.
  - Plugins: marketplaces (`extraKnownMarketplaces`) and plugins (`enabledPlugins`, `true` = install) both live in `claude/settings.jsonc.j2` — single source of truth; `install.py` applies them via the `claude` CLI (idempotent no-ops when present, skipped with a warning when the CLI is missing). The installer warns when a user-scope plugin is installed on the machine but missing from the repo config.
  - MCP: Claude Code can't read `mcp/servers.jsonc` (opencode format), so `install.py` translates it into `claude/plugins/mcp/.mcp.json` — our own plugin under the `patjlm-agents-config` marketplace. Per-server `"claude"` overrides in `mcp/servers.jsonc` handle differences (e.g. `exclude` for servers provided by other plugins). The rendered `.mcp.json` is gitignored (generated file). Per-server agent overrides: a per-agent key (e.g. `"claude"`) is deep-merged over the base server when rendering for that agent (dicts merge per-key, scalars/lists replace; `"exclude": true` skips the server). Base values use opencode syntax — `{file:PATH}` secrets are read by opencode at runtime; the claude rendering translates `{env:VAR}` to `${VAR}` and rejects `{file:...}` (claude can't read files), so override such values in the `"claude"` block with an env-var ref. Never inline secret contents. Directory-marketplace plugins load in place: edits apply on next session start or `/reload-plugins`.
- Codex specifics:
  - `codex/config.toml.j2` renders to `~/.codex/config.toml` — drift-aware like claude settings (`codex mcp add` writes there); `~/.codex/AGENTS.md` is generated (common + `codex/AGENTS.md`); enmaas model profiles render as `~/.codex/<name>.config.toml` (`codex --profile <name>`).
  - MCP: stdio servers translate natively (`cwd` is a codex key); `{env:VAR}` env entries become `env_vars` forwarded from codex's environment (renamed vars get a bash wrapper); http servers need a `"codex": {"bearer_token_env_var": ...}` override — codex can't read `{file:...}` secrets either.
  - EnMaaS: codex only supports the responses wire API (`/v1/responses`); the GLM default model assumes EnMaaS serves it over responses (the gpt-* profiles use the same endpoint). API key: read from the secret file via the provider `auth` command (`cat` + absolute path — codex has no file references or env expansion in config; MCP secrets are env-only via `env_vars`/`bearer_token_env_var`). `features.fast_mode = false` while enmaas is enabled — EnMaaS rejects `service_tier=priority` ("Fast").
  - `/model` picker: codex's catalog doesn't know the EnMaaS models and `model_catalog_json` *replaces* it, so with enmaas enabled `install.py` generates `~/.codex/model-catalog.json` (GLM + DeepSeek + the gpt-* profile models, no Fast tiers) from the catalog bundled in the codex binary (`codex debug models --bundled`; skipped with a warning if codex is missing). EnMaaS-only entries (GLM, DeepSeek) are synthesized keeping only codex's required fields — copying GPT-specific capability flags (`supports_search_tool`, freeform `apply_patch`, …) breaks their vLLM backends. If a codex upgrade changes the schema, re-run install; if generation fails the picker just loses those models.
  - Reasoning effort: GLM runs at `high` (set in `config.toml`, and the only level its catalog entry offers — codex doesn't apply catalog defaults on its own). Profile files layer over `config.toml`, so each profile pins its model's own default effort (`CODEX_PROFILES` in `install.py`) instead of inheriting GLM's — the `deepseek` profile (secondary EnMaaS option next to GLM, vision-capable) pins medium.
- omp specifics:
  - `omp/models.yml.j2` renders to `~/.omp/agent/models.yml` — EnMaaS providers under their own IDs (built-in `openai`/`anthropic` stay unchanged), including `enmaas-anthropic` (Claude opus/sonnet/haiku 5.5) with the three gateway overrides EnMaaS requires — `headers.X-Api-Key`, provider-level `disableStrictTools`, `compat.supportsContextManagement: false` (details in `omp/README.md`). The API key is read from the secret file at request time via the command form (`!cat` — quoted, a leading `!` would otherwise parse as a YAML tag); no env vars. `mcp/servers.jsonc` translates to `~/.omp/agent/mcp.json`: `{file:PATH}` → `!cat PATH`, `{env:VAR}` → `!printenv VAR` (omp runs `!` values as shell commands at connect time; `Bearer {file:...}`-style headers become `!echo "Bearer $(cat ...)"`).
  - `~/.omp/agent/AGENTS.md` is generated (common guidelines) — without it omp falls back to reading `~/.claude/CLAUDE.md` (foreign-config discovery).
  - `~/.omp/agent/config.yml` is omp-owned (`/settings`, `omp config set` write there) — never rendered wholesale; `install.py` only sets `modelRoles.default`/`modelRoles.advisor` and `advisor.enabled` surgically (EnMaaS DeepSeek main + GLM advisor when enabled, the `openai-key` fallback provider alone when disabled — same key file and default model as opencode's fallback), preserving omp's own settings.
- pi specifics:
  - `pi/models.json.j2` renders to `~/.pi/agent/models.json` — the omp EnMaaS provider set (glm, deepseek, openai) plus `enmaas-anthropic` (Claude opus/sonnet/haiku 5.5 over EnMaaS's anthropic-compatible endpoint) and the litellm local proxy carried over from the pre-repo setup; apiKey via `!cat` at request time (unlike omp, a bare apiKey value in pi is a literal, not an env-var name). EnMaaS's older Anthropic validation rejects message-level `output_config` and body `betas`: keep `compat.supportsMidConvoEffort` false. All three 5.5 models are adaptive (`forceAdaptiveThinking`), so pi skips the budget-thinking `betas` field (details in `pi/README.md`). `mcp/servers.jsonc` translates to `~/.pi/agent/mcp.json` via the shared pi-family `!command` translation (needs pi 1.x — built-in MCP).
  - `pi/settings.json.j2` renders to `~/.pi/agent/settings.json`, drift-aware like claude settings (pi writes theme, packages, changelog version there). `defaultProvider`/`defaultModel` switch with `enmaas.enabled`; the disabled fallback is the vertex provider (pi-vertex extension, gcloud ADC) with `claude-opus-4-6` — haiku-4-5 rejects adaptive thinking on vertex, and `modelOverrides` cannot reach extension-registered models to disable it.
  - `@lhl/pi-vertex` 1.1.9 (latest, May 2026) predates pi 1.x — `install.py` patches the installed copy in `~/.pi/agent/npm/` with the fix proposed in its issue #2 (unreleased upstream); drop the patch when a fixed version ships.
  - `pi/extensions/` and `pi/settings/` (pi-vertex) hold the addons gathered from the pre-repo setup, symlinked 1:1 into `~/.pi/agent/` (individually, so runtime-written `*.config.json` files next to the extensions stay unmanaged). Extension backups go under `~/.pi/agent/backups/` — a `.bak` inside `extensions/` would be discovered as an extension.
  - The installer never touches `~/.pi/agent/{auth.json,sessions,run-history.jsonl,models-store.json,bin,npm}` — pi-owned/user data.

## Python scripts

- All Python scripts run via `uv` with PEP 723 inline dependency headers (`# /// script`). No venvs, no pip install. Run as `uv run <script>.py`.

## Repo nature

- **Never commit sensitive info** (credentials, tokens, API keys, secrets). Configs may be shared/synced widely — assume anything here is public.
- Config files must not reference sensitive files inside this repo, even if gitignored. Reference them by absolute path outside the repo instead (`~` or `$HOME`, e.g. `~/.secrets/openai.key`).
- Config + scripts only (Python via uv, shell). No build, test, or lint toolchain.
- Verify changes by running `make check` (validate renders without installing) — `make plan` adds a unified diff of every file that would change, which is how to preview an `mcp/servers.jsonc` edit in each agent's native format — then `make install` (expect `unchanged:` on re-run), and exercise the affected agent.
- OpenCode v2: the published schema (https://opencode.ai/config.json) accepts v2 keys (`permissions`, `providers`), so `install.py` validates the rendered config against the vendored `opencode/config.schema.json` and rendered opencode subagent templates as v2 `agents` entries. Refresh the snapshot when upgrading OpenCode: `curl -fsSL https://opencode.ai/config.json -o opencode/config.schema.json`. V2 vs V1: model capabilities are `capabilities` (not `modalities`), providers use `package`/`settings` (not `npm`/`options`), and agent rules are `permissions` — an ordered `{action, resource, effect}` list where the last match wins and unmatched rules default to `ask`; `bash`→`shell`, `task`→`subagent`, and writes split across `edit`/`write`/`patch`. `~/.config/opencode/AGENTS.md` is auto-loaded, so never also list `~/.agents/AGENTS.md` under `instructions` — it holds the same common text and loads twice; `instructions` is only for extra files/globs. OpenCode's own `~/.config/opencode/skills/` is not managed by the installer (it scans `~/.claude/skills` and `~/.agents/skills` instead) — stale copies there shadow the repo versions, so keep it for OpenCode-only skills.
